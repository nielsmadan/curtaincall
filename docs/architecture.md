# Architecture

The CLI is the compatibility boundary. Internal Python functions and dataclasses are not a public library API. The runtime uses only the standard library; consumer-specific preparation and publication remain outside the engine.

[models.py](../src/curtaincall/models.py) holds the frozen dataclasses every module passes around: the loaded policy, inspected repository snapshots, proposals and requests. [config.py](../src/curtaincall/config.py) turns strict JSON into those frozen policy values and owns the stage template fields; its allowed keys are the `ReleaseConfig` and `Stage` field names, so a new key needs only a field and its parsing. [versions.py](../src/curtaincall/versions.py) makes deterministic version decisions from inspected history; versions travel as integer tuples and are formatted only for tags, templates and output. [process.py](../src/curtaincall/process.py) runs subprocesses: environment filtering, `run_command` (raises on failure) and `run_process` (returns a `ProcessResult` for callers such as `gh` and `ls-remote` whose nonzero exits are data), with one failure format, `WHAT failed (CODE): DETAIL`, and URL userinfo redacted. [git.py](../src/curtaincall/git.py) holds Git plumbing on top of it: the fixed safety options, revision and ref queries, ref-name helpers, changed-path listing, root and policy-location discovery and the GitHub origin match that `curtains ci` builds on. [inspection.py](../src/curtaincall/inspection.py) applies the release preconditions (branch, cleanliness, single origin destination, historical tag agreement) and produces the reviewed snapshot and release state. [stages.py](../src/curtaincall/stages.py) runs preparation stages and enforces stage integrity; [leftovers.py](../src/curtaincall/leftovers.py) describes what a failed or cancelled preparation left behind. [release.py](../src/curtaincall/release.py) orders those boundaries and owns the preview, confirmation, tagging, the push and the final report. [ci.py](../src/curtaincall/ci.py) implements `curtains ci`: tag-validation and previous-tag policy over the Git queries, and the `publish` argument handling. [publish.py](../src/curtaincall/publish.py) holds GitHub release publication: pure comparison of an existing release with the expected one into a plan of removals, uploads and publication, and the `gh` calls that execute it. [pins.py](../src/curtaincall/pins.py) implements `curtains pins`: pure version, reference-rewrite and report functions, and the `gh release view`, `gh api` and `gh release download` calls; [config.py](../src/curtaincall/config.py) parses and serializes the pins file. [errors.py](../src/curtaincall/errors.py) defines `ReleaseError`, `ReleaseCancelled`, `NothingToRelease` and the message helpers `short_id` and `name_list`. [arguments.py](../src/curtaincall/arguments.py) defines the location options every command line shares: `--directory` and a file option, `--config` for the release policy or `--file` for pins. [cli.py](../src/curtaincall/cli.py) owns arguments, help, installed version metadata, the interactive prompt, top-level errors and exit status: `NothingToRelease` exits 3 and `ReleaseCancelled` exits 130 when its `left_changes` is set.

`ReleaseState.latest` and `TagState.version` hold versions as integer tuples without a prefix; `TagState.name` retains the full tag name. CLI and custom-suggestion inputs accept a configured prefix only when the input is not already a canonical numeric version. This order also supports numeric tag prefixes.

The boundary between engine, CI commands and consumers: the engine owns local preparation, the annotated tag and the atomic push. `curtains ci` owns tag validation and GitHub release verification and publication, run from the tag-triggered workflow. Registry publishing, manifest and prerelease decisions and the choice of assets stay in consumer code. The CI origin check is `matches_repository` only, comparing the origin URL with `repository`; it does not use the release engine's destination inspection.

`cli.main` routes to `curtains pins` only when `pins` is the first argument, and pins options follow it, because pins use `--file` rather than the release policy's `--config`. Pins live in curtains because the release side already produces the GitHub releases and digests they consume, and every consumer already has `curtains` installed. Digests are recorded from GitHub's server-side asset digest rather than from a `SHA256SUMS` asset downloaded alongside the files, and `fetch` verifies against the committed digest, so a release asset replaced after pinning cannot pass unnoticed.

`curtains ci` lives in curtains because the policy file already defines the tag namespace, version parts, branch and repository, so a consumer's workflow cannot drift from the release command's rules. `cli.main` routes to it when the first argument after any `--config`/`--directory` options is exactly `ci`; no version or bump override can be that string, so the release grammar is unchanged. The `ci` commands read the policy with `load_tag_policy`, which validates only the tag and publication fields they use and ignores release-only sections and unknown keys, so a tag-triggered workflow pinned to an older `curtains` still reads a policy that gained release-only keys. The CI origin check is deliberately weaker than the release engine's: `actions/checkout` controls origin in CI, so rewrite and single-destination inspection would only reject valid runners. Prerelease and latest state are `publish` flags, not policy fields, because they depend on the version or manifest, which consumers own.

`publish` creates a draft, uploads, then publishes, so a release is never visible with missing assets, and each step is idempotent against the `gh release view` state. It only completes drafts and refuses to mutate a published release (divergent bytes, incomplete assets, immutable releases): rewriting published assets automatically is riskier than one documented manual step. Relative `--notes` and asset paths resolve against `--directory`, like `--config`, so one rule covers every `ci` path argument.

The GitHub Action installs from its own checkout with `scripts/install_action.py`: a launcher that runs `curtaincall.cli.main` from the checkout's `src` under `python -I`, plus a minimal `curtaincall-VERSION.dist-info` so installed-version lookup works. This keeps the job free of network access, pip, build backends and a PyPI distribution; the action pin is therefore the `curtains` version. The installer runs before anything is installed and must stay standard-library-only.

The lifecycle is inspect → tool check, signing check and custom suggestion → propose → preview → preflight checks → confirm → revalidate → prepare stages → revalidate → annotated tag → atomic push → report. Dry-run skips the tool check, signing check and suggestion and ends after the preview, without executing any configured command. A real run without `--yes` and without a terminal stops before any of those commands. Revalidation re-reads only the snapshot (`inspect_snapshot`), not the history and ahead count. `_prepare_and_tag` covers prepare stages → revalidate → annotated tag: a failure or interruption there is re-raised with a summary of the local leftovers, gathered by `collect_leftovers` and formatted from the plain `Leftovers` value, whose `changed` property decides `left_changes`. Gathering failures, including a second interruption, fall back to a generic summary without hiding the original error. Loaded configuration stays fixed throughout a run.

The reviewed snapshot (`RepositorySnapshot`) binds HEAD, branch, cleanliness, origin destination, remote release branch and the entire matching historical tag namespace. Preparation may advance HEAD only through the engine's own single-parent stage commits. Origin and historical refs are checked again before tagging. Unrelated branches and tag namespaces are outside this snapshot.

Stage integrity compares changed paths without rename heuristics, validates directory boundaries and symlinks, and captures the staged tree before commit. Hooks remain enabled. Each stage commit must have exactly the captured HEAD as its single parent and change only allowed paths. If hooks change allowed bytes, stage checks rerun against the resulting commit; without stage checks only scope/commit integrity is established. A dirty result, switched branch or extra commit stops the release.

The push targets the validated destination with exact prepared commit and annotated tag object OIDs, `--atomic --no-follow-tags --recurse-submodules=no`. It never forces, retries, rolls back or falls back to a non-atomic push. Atomicity covers the two remote refs, not local preparation, a global namespace lock or asynchronous publication. Concurrent actors can still change refs after revalidation.

Engine Git operations use `git_command` for literal pathspecs, replacement-ref suppression, disabled optional locks and disabled lazy fetching. Inspection asks `for-each-ref` and `ls-remote` only for the release branch and the policy's tag namespace, then filters exactly. Changed paths come from one `git status --porcelain=v1 -z --untracked-files=all --ignore-submodules=none --no-renames` call. `command_environment` clears inherited Git context while preserving non-Git variables and explicit Git authentication, transport and configuration controls. `run_command` captures bytes and decodes with `os.fsdecode`, without universal-newline conversion. Callers may strip scalar output, but must preserve NUL-delimited filename output so CR/LF and undecodable filename bytes round-trip.

Historical tag objects are peeled and validated together in one batch per inspection, including nested annotated tags. Missing history is an inspection failure, not an invitation to fetch. Commit-message extraction suppresses signature display so Git's display settings cannot alter version selection. These boundaries are tested with disposable repositories and bare local remotes, including a discriminating non-atomic push control.
