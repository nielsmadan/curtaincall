# Architecture

The CLI is the compatibility boundary. Internal Python functions and dataclasses are not a public library API. The runtime uses only the standard library; consumer-specific preparation and publication remain outside the engine.

[config.py](../src/curtaincall/config.py) turns strict JSON into frozen policy values; [versions.py](../src/curtaincall/versions.py) makes deterministic version decisions from inspected history. [git.py](../src/curtaincall/git.py) owns subprocess execution, root/destination discovery and read-only Git inspection, including the plumbing queries, origin check and `ls-remote` read that `curtains ci` builds on. [release.py](../src/curtaincall/release.py) orders those boundaries and controls stage commits, tagging and the push, plus previews, confirmation and progress output. [ci.py](../src/curtaincall/ci.py) implements `curtains ci`: tag-validation and previous-tag policy over those queries, and the `publish` argument handling. [publish.py](../src/curtaincall/publish.py) holds GitHub release publication: pure comparison of an existing release with the expected one into a plan of removals, uploads and publication, and the `gh` calls that execute it. `git.py` also defines `ProcessResult` (exit code, stdout, stderr) returned by `run_process`, for callers such as `gh` and `ls-remote` whose nonzero exits are data; `process_failure` formats such a failure with URL userinfo redacted. [cli.py](../src/curtaincall/cli.py) owns arguments, help, installed version metadata, top-level errors and exit status.

`ReleaseState.latest` holds the canonical numeric version without a prefix; `TagState.name` retains the full tag name. CLI and custom-suggestion inputs accept a configured prefix only when the input is not already a canonical numeric version. This order also supports numeric tag prefixes.

The boundary between engine, CI commands and consumers: the engine owns local preparation, the annotated tag and the atomic push. `curtains ci` owns tag validation and GitHub release verification and publication, run from the tag-triggered workflow. Registry publishing, manifest and prerelease decisions and the choice of assets stay in consumer code. The CI origin check is `matches_repository` only, comparing the origin URL with `repository`; it does not use the release engine's destination inspection.

`curtains ci` lives in curtains because the policy file already defines the tag namespace, component count, branch and repository, so a consumer's workflow cannot drift from the release command's rules. `cli.main` routes to it only when the first argument is exactly `ci`; no version or bump override can be that string, so the release grammar is unchanged. The CI origin check is deliberately weaker than the release engine's: `actions/checkout` controls origin in CI, so rewrite and single-destination inspection would only reject valid runners. Prerelease and latest state are `publish` flags, not policy fields, because they depend on the version or manifest, which consumers own.

`publish` creates a draft, uploads, then publishes, so a release is never visible with missing assets, and each step is idempotent against the `gh release view` state. It only completes drafts and refuses to mutate a published release (divergent bytes, incomplete assets, immutable releases): rewriting published assets automatically is riskier than one documented manual step. Relative `--notes` and asset paths resolve against `--directory`, like `--config`, so one rule covers every `ci` path argument.

The GitHub Action installs from its own checkout with `scripts/install_action.py`: a launcher that runs `curtaincall.cli.main` from the checkout's `src` under `python -I`, plus a minimal `curtaincall-VERSION.dist-info` so installed-version lookup works. This keeps the job free of network access, pip, build backends and a PyPI distribution; the action pin is therefore the `curtains` version. The installer runs before anything is installed and must stay standard-library-only.

The lifecycle is inspect → propose → preflight checks → confirm → revalidate → prepare stages → revalidate → annotated tag → atomic push → report. Dry-run ends after preview, without executing any configured command. Loaded configuration stays fixed throughout a run.

The reviewed snapshot binds HEAD, branch, cleanliness, origin destination, remote release branch and the entire matching historical tag namespace. Preparation may advance HEAD only through the engine's own single-parent stage commits. Origin and historical refs are checked again before tagging. Unrelated branches and tag namespaces are outside this snapshot.

Stage integrity compares changed paths without rename heuristics, validates directory boundaries and symlinks, and captures the staged tree before commit. Hooks remain enabled. Each stage commit must have exactly the captured HEAD as its single parent and change only allowed paths. If hooks change allowed bytes, stage checks rerun against the resulting commit; without stage checks only scope/commit integrity is established. A dirty result, switched branch or extra commit stops the release.

The push targets the validated destination with exact prepared commit and annotated tag object OIDs, `--atomic --no-follow-tags --recurse-submodules=no`. It never forces, retries, rolls back or falls back to a non-atomic push. Atomicity covers the two remote refs, not local preparation, a global namespace lock or asynchronous publication. Concurrent actors can still change refs after revalidation.

Engine Git operations use `git_command` for literal pathspecs, replacement-ref suppression, disabled optional locks and disabled lazy fetching. `command_environment` clears inherited Git context while preserving non-Git variables and explicit Git authentication, transport and configuration controls. `run_command` captures bytes and decodes with `os.fsdecode`, without universal-newline conversion. Callers may strip scalar output, but must preserve NUL-delimited filename output so CR/LF and undecodable filename bytes round-trip.

Historical tag objects are peeled and validated together in one batch per inspection, including nested annotated tags. Missing history is an inspection failure, not an invitation to fetch. Commit-message extraction suppresses signature display so Git's display settings cannot alter version selection. These boundaries are tested with disposable repositories and bare local remotes, including a discriminating non-atomic push control.
